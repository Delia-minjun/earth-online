## 开发约定（改代码前必读）

1. **先定位根因，再动手。** 任何修改或 bug 修复，必须先说清楚「为什么会这样」——哪个文件、哪一行、在什么条件下触发、怎么复现。解释与复现对得上，才允许改代码。
   - 禁止试错式连续打补丁：**连续两次没修好，说明根因还没找到**，停下来重新定位，而不是再试一版。
   - 反例：三列布局连改三版都没生效，前两版都在猜宽度阈值，真正原因是 Tailwind 把 `min-[1150px]:` 排在 `lg:` 之前导致规则被覆盖。
2. **改完必须三件事都能过**：`typecheck`（server + web）、测试（47 个用例）、`vite build`。
3. **测试文件必须分开进程跑**（每个文件用自己的临时库），合并跑会互相污染数据。
4. **界面改动要在浏览器里刷新确认**，不能只凭代码判断生效。
5. **不碰用户真实数据做测试**：测试一律用临时目录，清理干净再收工。
6. 文档跟着代码走：改了行为就同步改需求/技术方案/README，不要让文档落后于实现。
7. **端口固定 `7788`，不要改。** 任何情况下都只跑一个实例，跑在 7788 上。
8. **重启服务的固定流程**（改完服务端代码时必须走一遍）：
   1. 先提示用户关闭他自己开的那个黑窗口（`start.cmd` / 桌面图标起的）；
   2. 确认 7788 已释放（`netstat -ano | findstr :7788` 无 LISTENING）；
   3. 由助手启动服务；
   4. 启动后必须验证：`/api/health` 返回 ok，且**新功能确实加载**（例如新字段出现在返回里），不能只看进程还活着。
   - 反例：有次验证全返回 `undefined`，以为是代码写错，实际是请求打到了用户自己开的旧实例上——旧进程没关，新进程 `EADDRINUSE` 起不来，健康检查却照样通。
9. **新功能优先用弹窗，不要往页面里塞。** 如果新功能是"在已有功能上继续加"（比如给任务加 DDL、给课程加周次），一律做成弹窗/抽屉，从现有按钮打开；**不改变原页面的布局与视觉节奏**。
   - 判断标准：加了新功能之后，原来那屏的卡片数量、排列、留白不应该变。
   - 反例：DDL 第一版直接插在输入框下面展开一行日期选择器，把「今日任务」的行高撑开了；后来改成弹窗才回到原样。
   - 例外：只有当新功能本身就是页面主体（比如整个新页面）时，才不用弹窗。
10. **行内操作按钮一律垂直居中。** 列表行里的 `＋` / `×` / `改` / `DDL` 这类小按钮，必须相对**整行内容**垂直居中，不能只贴在标题那一行。
   - 做法：把按钮作为行容器的直接子元素并加 `self-center`；不要塞进"标题那一行"的 flex 里。
   - 判断标准：行内容变成两行（标题 + 副标题）时，按钮仍在中间。
   - 反例：日历页的 ＋ 一开始放在内容容器里，容器是 `items-start`，于是按钮贴在行顶。

## 需求速览

1. 以「周」为单位的计划系统，承接原 Excel 周计划表的全部 15 个功能块。
2. 三端同步：电脑（主工作台）+ 平板（纸张替代）+ 手机（打卡 / 记一笔 / 看今天）。
3. 学习 Agent：分科建档、OCR + 校对、间隔重复复习、考前模拟与背记卡片。走 API。
4. 奖惩经济：做实事赚虚拟币，用币兑换自己定的奖赏；进度条会衰减，但不扣币、不负债。
5. 中英双语：一键切换，AI 内容跟随界面语言；点词查义 + 生词本 + 术语对照表。
6. 离线优先：打卡、随手记、记账、体重可离线写，联网自动合并。
7. 本地部署：先跑在本机，架构预留上云余地。

## 关键约束

- 数据在自己手里，可导出、可备份。
- 游戏化不能影响真实数据；惩罚只作用于进度条。
- 界面英文人工撰写，不机翻。
- i18n 从第一版就做，不做事后补。
